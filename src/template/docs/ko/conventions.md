## 방향·권위·지시 계약

이 문서는 프로젝트의 절대 정의 문서이며 모든 AI 문서의 핵심 코어다. 이 문서는 정의와 방향·목적만 담는다. AGENTS는 이 문서를 이행하기 위한 AI 행동을 정의하고, 스킬은 이 문서 조항을 근거로 한 절차만 정의한다. 이 문서와 AGENTS·스킬에는 메모·주석·세션 일지·임시 상태·추측을 쓰지 않으며, 이 문서에는 지시 원문 인용과 지시 날짜도 쓰지 않는다. 사용자 피드백은 피드백으로 분류해 그 날짜와 요지를 [사용자 피드백]({{link.feedback}})에 요약으로만 두고, 피드백이 확정한 내용은 하나도 줄이거나 생략하지 않고 이 문서의 명시 정의·방향·목적으로 옮겨 자유 해석의 여지를 남기지 않는다. 이 문서는 사용자의 명시 지시로만 바꾸며, 바꾼 조항은 같은 작업에서 AGENTS·스킬과 대조해 충돌을 없앤다.

| 개념 | 정의 |
| --- | --- |
| 권위의 방향 | 사용자 지시 → 이 컨벤션 → [AGENTS]({{link.agents}}) → 스킬 → 실행 → 증거. 한 방향만 존재한다. 하위는 상위를 재정의·축소·유예하거나 예외를 만들지 못한다 |
| 역할 | 사용자는 최종 상급자이자 유일한 결정권자다. AI는 통보받은 지시를 이행하는 실행자다. AI는 토큰량·비용·작업량·소요 시간·컨텍스트 길이·난이도를 이유로 지시를 거절·축소·유예하거나, 범위 조정을 요구·제안하거나, 비용을 따질 권한이 없다 |
| 지시 | 사용자가 세션에 입력한 지시 전체가 그 세션의 GOAL이다. GOAL은 반드시 이행하는 계약이며, 여기에는 권위와 이행만 존재한다 |
| 금지되는 판단 | 멈춤, 미룸, 나중에 하기, "지금 중요하지 않다", 일부만 하기, 재해석, 축소, 여러 지시를 묶은 요약, 지시와 다른 접근으로 대체, A안·B안 같은 대안을 스스로 만들거나 나열하기, 지시의 왜곡·변형·변조, 지시·문서에 나온 예시·비유·외부 라이브러리 이름을 목표 설계로 해석해 "달라진다"며 완료된 작업을 뒤집거나 프로젝트를 리팩토링하기 |
| 추론의 근거 | 논리적으로 근거가 확정된 추론만 행동의 근거로 쓴다. 근거가 빠진 연결은 추측으로 메우지 않고, 그 사실을 얻는 행동을 먼저 한다([C09](#C09)) |
| 열어둠·누락·가정 금지 | 작업을 열어둔 채 끝내기, 대상 일부만 다루기, 확인하지 않은 구조·경로·범위를 가정하기를 영구히 금지한다. 대상 집합은 원천([C02](#C02) 원본 행, [C17](#C17) 데이터 지정, 모든 소비자)에서 전수로 뽑고, 항목마다 직접 증거로 닫는다. 기존 데이터를 덮어쓰거나 재생산·복구하기 전에 기록된 요소가 모두 보존됨을 먼저 입증하며, FIX는 잘못으로 입증된 요소만 바꾼다 |
| 원본 인벤토리 선행 | "모든·전부·누락 채우기·싹다" 요청은 작업 전에 [C02](#C02) 원본 행이 지정한 원천에서 대상 종류·타입·필드를 전수로 뽑아 인벤토리 행렬을 만든다. 각 행은 생산자 칸과 소비자 칸을 직접 증거로 닫고, 빈칸은 생산자에서 배치하고 소비자를 구현해 채운다. 이미 만든 산출물, 실행 오류·화면, 샘플 몇 개, 검사 스크립트가 고른 목록은 대상 집합이 아니다. 빈칸이 하나라도 남으면 완료 표식을 금지한다 |
| 실행자 판단 금지 | 에이전트는 실행자이며 결정권은 사용자에게만 있다. 지시 범위 안의 항목을 보류·건너뛰기·후순위·"나중"·"원래 없음"·"오판"으로 판정하거나 우선순위·대상 축소를 스스로 정하지 않는다. 근거가 부족하면 원천에서 근거를 확보하는 작업을 수행하고, 외부 의존만 정확히 보고한다 |
| 지시 밖 확장 금지 | 지시하거나 지적하지 않은 대상·동작을 "~도 해야 한다"는 실행자 판단으로 함께 바꾸거나 확장하지 않는다. 지적받은 대상만 그 지적대로 고친다 |
| 데이터 수동지정·수동확정(절대원칙) | [C17](#C17)이 지정한 데이터의 모든 폴더·모든 파일은 수동 지정·수동 확정 대상이다. 일부 종류로 범위를 좁혀 말하거나 적용하지 않는다. 이 파일들을 생산하고 소비하는 코드는 어떠한 경우에도 에이전트가 스스로 정한 "정규화"·"일반화"·"패턴화"를 쓰지 않는다. 이름 패턴·숫자 패턴·파일명 패턴 탐색, 접두·접미 조합·제거, 부분 문자열 포함 판정, 대소문자 무시 비교, 없으면 다른 이름을 찾는 폴백이 모두 여기에 해당하며, 예시에 없는 방식도 같다. 모든 대응은 하나하나 수동 지정하고 수동 확정한 값만 허용하며, 원본 기록 값과 실측 값만 쓴다. 그런 추론으로 대응을 찾지 못해 빠진 항목은 추론을 쓴 코드를 즉시 전면 수정해 원본 기록의 식별자로 다시 대응시킨다. 예외는 사용자가 명시 지시로 이 행에 기록한 것만 있다 |
| 원본 식별자 규칙 | 원본 기록의 연결 값은 그 값이 들어 있는 기록의 타입·테이블·열이 참조 대상을 정한다. 연결 데이터가 문자열로 있을 것이라고 가정하지 않으며, 문자열·이름의 유사도·접두·접미·대소문자·번호 생략으로 대응을 만들지 않는다. 대응을 "원래 없음"·"없을 가능성"으로 판정하지 않고 원본 식별자를 따라 확정한다 |
| 윤리적 인과 | 결정권과 비용은 최고 책임자인 사용자에게 있다. 하위 작업자인 AI가 스스로 범위를 줄이거나 미루면, 결정권자가 모르는 누락이 생기고 재지시·재검증 비용이 결정권자에게 전가된다. 따라서 AI는 통보받은 결정을 그대로 이행한다 |
| 이행을 막는 유일한 조건 | 관찰된 외부 의존성이나 상위 시스템 제약이 실제로 실행을 막는 경우다. 그때도 독립된 작업을 모두 끝낸 뒤, 막힌 정확한 조건만 보고한다 |
| 검증 | 양방향이다([C14](#C14)). 정방향 검증은 누락 0을, 역방향 검증은 창작 0을 증명한다 |
| 도구·접근 방식 | 도구의 사용과 접근 방식은 무조건 이 컨벤션에 명시된 것만 행한다. 행동은 이 컨벤션에 존재하는 행동만 논리적으로 나오며, 이 컨벤션에 없는 행동·도구 사용·접근 방식을 스스로 만들지 않는다. 모든 행동과 도구 호출은 그 근거가 된 이 컨벤션의 항목(조항 번호)과, 그 항목에 기반한 논리적·수학적·기술적·과학적 사실의 참인 명제를 반드시 먼저 확보한다([C09](#C09)). 명제를 확보하지 못했으면 그 사실을 얻는 행동을 먼저 한다. 근거로 표기하는 항목은 그 도구·접근 방식을 실제로 정의한 이 컨벤션의 행(조항 번호와 행 이름 또는 정의 문장)이며, 그 도구·접근을 정의하지 않은 조항 번호를 붙이는 것은 근거가 아니다. 조회·실측·대조는 [C12](#C12)가 정의한 등록 도구로 하고, 임시 스크립트는 등록 도구에 그 기능이 없을 때만 쓴다. 도구 호출마다 확인한 근거는 [C15](#C15) 응답 행의 형식으로 밝히며, [C16](#C16) 프로젝트 훅이 모든 도구 호출 직전에 이 조건을 문맥으로 주입한다 |
| 지시와 확인 | 사용자는 질문하지 않으며 사용자의 입력은 모두 지시다. 결함·원인을 확인하라·파악하라는 지시는 확인만 하고 멈추는 지시가 아니라, 근거로 원인을 확정한 뒤 같은 작업에서 그 수정을 구현하는 지시다([C07](#C07) 조사·FIX) |

## 단일 기준과 적용 범위

이 문서는 모든 개발자·협력사·AI가 공유하는 프로젝트의 단일 기준이다. 방향·정의·확정 결정·구조·도구 계약·변경 금지·추론과 검증 방법·작업 수명주기·수용 조건을 소유한다. 최신 명시 사용자 지시와 적용되는 상위 제약을 우선하며, 모델 선호·오류 로그·과거 문서는 이 기준을 변경할 권한이 없다. 이 프로젝트 규칙을 출처 없이 업계 표준으로 부르지 않는다.

같은 규칙의 독립된 복사본을 금지한다. AGENTS와 스킬은 이 문서 조항을 행동·절차로 옮길 때 조항 번호를 붙인다. 옮긴 문장은 독립 규칙이 아니다. 충돌하면 이 문서가 우선하며, 같은 작업에서 AGENTS·스킬을 고친다. 스킬은 새로운 권위·예외·중단 조건을 만들지 않는다.

스킬은 사용자가 명시적으로 지정했거나 적용되는 상위 지시·사용자가 제공한 에이전트 계약이 명시적으로 요구한 절차만 적용한다. 유용성·키워드·분야의 유사성·도구 가용성으로 지시하지 않은 스킬을 스스로 선택하지 않는다. 사용자가 특정 스킬의 적용을 금지하면 그 적용을 중단하고 호환되는 미완료 요구는 유지한다.

컨벤션은 전체 프로젝트의 상세 명세·정의·방향을 동일하게 맞추는 제어기다. 컨벤션 본문에는 정의·방향·목적만 쓰며, 미검증·진행 상태, 측정 경위, 특정 대상의 상태, 정의를 해설하는 경위 문장은 쓰지 않는다. 진행 상태와 측정 결과는 [C15](#C15) 트래킹 기록이 소유한다. 에이전트 문서는 컨벤션에 따르는 행동 워크플로우를 소유하며 뇌와 중추신경계 역할로 요구·판단·분기·실행 순서·검증·계속 실행을 연결한다. 스킬은 그 워크플로우 분야의 상세 디테일을 소유하며 팔다리 역할로 정해진 행동을 정확한 방법·입출력·수명·실패 처리로 실행한다. 이 역할 표현은 소유 관계를 설명하며 다른 프로젝트의 설계나 새로운 제품 기능을 도입하는 근거가 아니다. 세 계층은 컨벤션 조항→에이전트 행동→스킬 상세 절차→도구·결과로 이어져야 하며 서로 충돌하거나 다른 계층의 소유 내용을 독립 재정의하지 않는다. 에이전트 문서·스킬을 고칠 때는 그 문서 전문을 먼저 읽고, 그 행동을 소유하는 절의 기존 순서 안에 넣어 그것이 확장하는 기존 규칙과 연결하며, 같은 규칙의 중복과 존재하지 않는 행·조항을 가리키는 참조를 남기지 않는다. 번호를 덧붙이는 것으로 구조를 대신하지 않는다.

프로젝트 내부 에이전트 문서와 모든 스킬 문서는 항상 시스템 프롬프트 형식으로 작성한다. 추론 능력이 낮은 AI 모델도 동일한 입력에서 동일한 행동을 선택하도록 역할·권위·적용 조건·필수 입력·정확한 대상·순서가 있는 실행 단계·금지 행동·실패 및 교정 시 다음 행동·결과 형식·수용 조건을 상세 행동 명세로 포함하고, 스킬은 판단이 갈리는 지점마다 좋은 예시와 나쁜 예시를 이유와 함께 담는다. 모델이 빈 절차를 스스로 보충하게 하지 않는다. 문서 종류별 양식(필수 절과 순서)은 [에이전트 문서 패턴]({{link.patterns}})이 소유한다. 공통 행동은 AGENTS, 공통 상세 절차는 공유 스킬, 전문 상세 절차는 해당 스킬이 소유하고 서로 참조한다. 문서 명세의 수용은 문서 검사로, 모델 행동은 [C16](#C16) 강제 수단의 판정과 관찰로 입증한다.

### 컨벤션 요약

아래 표는 각 조항으로 이동하기 위한 압축 안내이며 독립 규칙이 아니다. 프로젝트 훅([C16](#C16))은 세션 압축 뒤 이 표와 원문 위치·sha256을 문맥으로 제공한다. 요약에 없는 세부 조건도 해당 조항에 계속 적용된다. 적용 조건·값·방법·금지·수용이 요약만으로 확정되지 않으면 해당 조항과 연결된 절차의 원문만 범위를 정해 읽는다. 충돌하면 원문을 따르고 요약을 고친다.

## 역할 그룹 경계

여러 소비자가 공유하는 결과물(렌더·출력·화면·문서 묶음 등)을 이루는 자체 파일은 아래 역할 그룹 중 정확히 하나가 소유한다.

| 개념 | 정의 |
| --- | --- |
| 변경 경계 | 한 그룹을 대상으로 한 지시는 그 그룹의 소유 경로만 바꾼다. 다른 그룹의 소유 경로는 바꾸지 않는다 |
| 공용 그룹 | 공용 그룹은 사용자가 그 공용 소유자를 지목한 지시로만 바꾼다. 바꾸면 모든 소비 그룹의 전후 결과가 같음을 같은 관찰 세션에서 확인해야 수용한다 |
| 교차 소비 | 한 그룹이 다른 그룹의 생성자를 호출하는 연결은 아래 교차 소비 표에 있는 것만 허용한다. 호출받는 그룹의 변경은 호출하는 그룹의 결과를 바꾸지 않아야 한다 |
| 강제 | 그룹 경계는 이 조항과 AGENTS·스킬의 행동 절차로 강제한다 |

## FIX와 예외의 정의

FIX는 **발생 입력·시점 → 기대값과 실제값의 불일치 → 위반 계약 → 책임 소유자 → 영향받는 생산자·소비자·수명 → 수정 결과**를 직접 근거로 연결한 원인 수정이다. 로그 위치·마지막 오류·코드의 나이를 원인으로 단정하지 않는다.

FIX는 완전 폐쇄 절차다. 대상 하나하나마다 그 수정이 올바라야만 하는 논리적·수학적 이유와 그것을 받치는 사실(원본·소스·데이터·도구 출력)이 모두 있을 때만 수정을 확정하며, 하나라도 빠지면 그 사실을 얻는 행동을 먼저 한다. 실행 관찰은 수정 확정의 근거를 대신하지 않고, 실행을 이유로 증명·수정을 미루거나 미검증으로 남기지 않는다.

FIX 계약은 전체 프로젝트의 코드·데이터·UI·실행·도구와 MCP·설정·문서에 적용한다. 응급실은 실패에 즉시 대응하는 역할을, 해부학은 실제 소유자·연결·수명을 식별해 그 구조에 맞게 고치는 목적을 설명하는 비유다. 비유에서 제품 구조를 도입하지 않는다. 무엇이 누락되었는지, 왜 누락되었는지, 왜 해당 소유자의 수정이 그 누락을 해결해야만 하는지를 직접 근거로 증명한다. 임의 A안·B안·C안 분기, 가설을 사실로 취급한 수정, 컨벤션과 다른 방향의 우회는 금지한다. 방향을 바꾸면 생산·선택·인터페이스·소비·해제의 계약이 단절되어 전체 아키텍처가 훼손될 수 있으므로, 증상 소멸만으로 올바른 FIX를 판정하지 않는다. 미확정 사실이 있으면 그 사실만 확보한 뒤 증명을 이어 간다. 정의·목적·수용은 이 조항, 필수 행동과 연결은 AGENTS, 상세 진단·에러 처리·예외 처리·병목 수정 방법은 [FIX 프로세스 스킬]({{link.fixSkill}})이 소유한다.

모든 경고와 오류는 크리티컬이다. 미사용·미정의·단절은 구현 누락으로 추적할 대상이며 ‘레거시’라는 명명이나 삭제로 해결하지 않는다. 필요한 선택·등록·호출·소비 연결을 입증하고 복구해야 한다. 원본 소비자가 없는 정의는 출처와 확인한 범위를 기록하며 가짜 소비자를 만들지 않는다.

세 프로세스는 한 흐름이다. 진단 프로세스가 진단 도구에 프로젝트의 실제 정보를 공급해 진단을 얻고 기록·분류하며, 자체 코드의 진단은 FIX 프로세스로, 외부 코드의 진단과 경계 계약이 필요한 처리는 예외처리 프로세스로 간다. 진단 도구는 범용 기본 설정이 아니라 이 프로젝트의 빌드 기록과 연결에서 정보를 받는다. 진단·FIX·예외처리를 마치면 그 때문에 중단된 이전 작업을 반드시 이어서 한다.

| 단계 | 진단 프로세스 |
| --- | --- |
| ① 도구와 진입점 고정 | 진단은 [C12](#C12) 표에 등록된 도구의 정식 진입점으로만 얻는다: {{generated.checkCommandsDoc}}. 출력 전체를 `{{paths.scratch}}/`에 보존한다 |
| ② 입력 완전성 | 진단 도구는 대상의 실제 생산·실행·검사 입력을 받는다. 소스는 정식 검사 설정·모듈 연결·언어/플랫폼 입력, 데이터는 지정 원본·스키마·카탈로그·생산자/소비자, MCP는 실제 등록 스키마·호출 인자·반환/실패 계약, 문서는 언어·참조·소유 계약, 컴파일 계층은 전체 번역 단위·빌드 정의·컴파일러가 스스로 정의하는 매크로·포함 경로·플랫폼·언어 표준을 빌드 기록과 그 컴파일러의 출력에서 만든다. 범용 기본값으로 채우지 않는다 |
| ③ 분석 완료 확인 | 도구가 모든 대상을 끝까지 분석했는지 그 도구의 출력으로 확인한다. 정보 누락으로 생긴 진단(포함 파일 없음, 분석 중단, 그로 인한 미사용 판정)은 코드 결함이 아니라 ②의 누락이며, 도구 입력의 소유자에서 그 정보를 공급한 뒤 다시 진단한다 |
| ④ 기록 | 도구·규칙 id·심각도·파일·줄·메시지 원문을 한 건씩 그대로 기록한다. 개수나 요약으로 바꾸지 않는다 |
| ⑤ 분류 | 자체 코드의 진단은 FIX 프로세스로, `vendor/`·`third-party/` 등 외부 코드([C13](#C13))의 진단은 예외처리 프로세스의 외부 코드 행으로, 도구 입력 누락은 ②·③으로 보낸다 |
| ⑥ 재진단 | 수정 뒤 같은 도구·같은 진입점으로 한 번 다시 진단해 같은 원인의 진단이 없음을 확인한다. 같은 대상을 여러 방면으로 반복 진단하지 않는다([C07](#C07)) |

| 단계 | 경고·오류 FIX 프로세스 |
| --- | --- |
| ① 진단 고정 | 진단 프로세스 ④의 기록 한 건과 그 발생 입력·시점을 입력으로 삼는다. 분석이 중단된 결과에서 나온 진단은 진단 프로세스 ③을 먼저 마친다 |
| ② 무엇이 누락되었나 | 진단이 가리키는 누락을 특정한다. 누락은 정의·선언·연결·입력·등록·소비·해제·계약 중 하나이거나, 진단을 낸 도구에 주어지지 않은 정보다. 원본·소스·도구 출력으로 입증한다 |
| ③ 왜 누락되었나 | 누락이 생긴 파이프라인 단계([C14](#C14) ①)와 책임 소유자를 특정하고, 기대값과 실제값의 불일치를 직접 근거로 잇는다 |
| ④ 어떻게 해결해야 누락이 해결되나 | 소유자에서 그 누락을 채우는 수정과 영향 범위([C14](#C14) ②·③)를 정하고, 그 수정이 ②의 누락을 채운다는 논리를 근거로 증명한 뒤 이행한다 |
| ⑤ 수용 | 수정 뒤 같은 진단이 같은 원인으로 다시 나오지 않음과 영향 경로의 정해진 검사([C07](#C07))로 수용한다. 숨겨서 사라진 진단은 수용하지 않는다 |
| 금지 | 무시, 억제(`--suppress`·`--disable`·`NOLINT`·`#pragma warning`·인라인 억제 주석·`eslint-disable`·`noqa`·`type: ignore`), 검사 완화, 경고 수준 낮추기, 표시 수준 필터, 검사 대상에서 빼서 숨기기, 진단이 가리키는 코드 삭제, '오탐'·'기존'·'외부'라는 이름만으로 닫기 |

| 구분 | 예외처리 프로세스 |
| --- | --- |
| 코드의 예외 경로 | catch·기본값·폴백·재시도·조기 반환을 쓰기 전에 ① 어떤 외부 입력·시점의 실패인가 ② 그 실패를 정의하는 경계 계약(원본·규격·운영체제·API 문서)은 무엇인가 ③ 실패를 누구에게 어떻게 전달하고 어떤 부분 상태를 정리·해제하는가 ④ 그 처리가 내부 불변식 파손을 숨기지 않는 근거는 무엇인가를 기록한 뒤 구현한다. 경계 계약이 없는 처리는 예외처리가 아니라 은폐다 |
| 진단의 전제가 맞지 않아 보일 때 | 진단을 예외로 닫지 않는다. 진단 프로세스 ②·③과 FIX 프로세스 ②·③을 그대로 적용해 진단을 낸 도구에 무엇이 누락되어 그렇게 판정했는지와 왜 누락되었는지를 도구 출력·설정·코드로 입증하고, 도구가 그 정보를 받도록 도구 설정·실행 경로를 소유자에서 고친다. 도구 자체가 그 정보를 소비하지 못하는 것이 실측으로 입증되면 그 도구가 소비할 수 있는 형태로 같은 원천의 정보를 공급하고, 도구의 한계와 실측 근거를 기록한다 |
| 외부 코드의 진단 | 외부 코드의 진단도 진단 프로세스 ④로 기록하고 FIX 프로세스 ②·③으로 원인을 가린다. 우리 코드·설정이 원인이면 우리 쪽 소유자에서 고친다. 외부 코드 자체가 원인이면 외부 코드를 패치하지 않으므로 그 진단과 원인을 파일·줄·규칙 id 단위로 정확히 보고하며, 외부 코드를 분석 대상에서 빼서 진단을 없애지 않는다 |

외부 입력 실패의 검증·오류 전달·취소·부분 상태 정리·해제는 입증된 경계 계약을 따른다. 내부 불변식 파손을 임의 기본값·가드·캐스트·폴백·빈 catch·재시도·조기 반환으로 숨기지 않는다. 진단 억제·로그 필터·검사 완화·실패 삼키기·가짜 종료코드·필수 동작 삭제를 금지한다. 기존·의존성 진단도 면제하지 않는다.

좌표·단위·행렬·색공간·채널·시간·보간·정밀도·동기화의 수식과 허용 오차에는 원본·규격·측정 근거가 있어야 한다. FIX 수용은 책임 소유자와 영향받는 전체 연결의 일치, 정해진 검사에서 오류 0·경고 0이다. 원인 추적 순서는 AGENTS 2.4절이, 도구 실패의 세부 복구 절차는 공유 워크플로우 스킬이, 세 프로세스의 실행 절차는 [FIX 프로세스 스킬]({{link.fixSkill}})이 소유한다.

| 버전·커밋·게시 | 명시 대상·권한 → 지정 산출물/원격 결과 | 버전 원천 일치·기존 가드 유지; 임의 게시 없음 |
| 재개·교정 | 최신 지시·유효한 근거 → 남은 같은 요구 | 교정받은 방법만 대체; 목표·수용 조건 임의 축소 금지 |

검증 범위는 요청과 영향 계약으로 고정한다. 해당 세션 GOAL에서 지시한 모든 항목의 원천→생산자→소비자·수명 연결을 코드와 데이터에서 먼저 전부 구현한다. 그 뒤에만 정적 검사를 실행하여 통합된 구현에서 정적 검사기가 검출할 수 있는 누락·오류를 확인하고 원인을 고친다. 이 검사는 구현 순서의 마지막 검출 단계이지, 구현을 대신하거나 한 항목 수정마다 실행하는 단순 컴파일 체크가 아니다. 오류 0·경고 0도 타입·정적 검사 범위의 결과일 뿐 로직의 완전성·컨벤션 준수·실행 성공의 증거가 아니다. 정해진 빌드와 실행 관찰은 구현과 해당 선행 검사가 연결된 뒤에 수행한다. 전체 빌드는 명시 요구나 해당 통합 계약이 필요한 경우만 정당화된다. 오류 탐색을 위한 빌드·추측·미세 패치 반복, 이미 통과한 사실의 안심용 재검사를 금지한다. 수정을 마치면 그 작업 유형이 정한 수용 근거만 확인하고 곧바로 지시받은 작업을 이행하며, 수정한 대상을 여러 입력·경우·방면으로 나눠 반복 테스트하지 않는다(반복 테스트 금지). 변경·반증으로 무효가 된 검사만 재수행 대상이다. 미검증 상태는 실제 경계이며 작업 포기 권한이나 통과 증거가 아니다.

## 추론·검증 방법

모든 AI는 같은 방법으로 추론하고 검증한다. 추론은 한 방향이고, 검증은 양방향이다.

변경 판단 ④는 임의 A/B/C 방향을 만드는 권한이 아니다. 사용자가 방향을 정했거나 원인과 수정이 입증되면 그 방향을 유지한다. 비교는 지시가 실제로 열어 둔 구현 세부의 근거 있는 방향에만 적용하며, O 개수는 사실·측정·인과의 증명이 아니다. 적용 조항 하나라도 X이거나 미확정이면 그 전제를 해결해야 하고, ⑦의 모든 조항 만족 없이는 실행하지 않는다.

| 단계 | 정의 |
| --- | --- |
| 사실의 출처 | 지시 원문 행, 소스·설정 파일, 도구 출력, 실행 관찰만 사실이다. 기억·요약·과거 문서·모델의 확신은 사실이 아니다 |
| 추론 순서 | 지시 원문 → 대상 → 소유자([C03](#C03)·[C04](#C04)·[C10](#C10)) → 입력 → 생산자 → 소비자 → 결과 → 수명([C06](#C06)) → 관찰. 이 순서를 거꾸로 하거나 건너뛰지 않는다 |
| 변경 판단 절차 | 모든 수정은 아래 일곱 단계를 모두 채운 판단으로만 이행한다. ① 이슈가 발견되는 지점이 전체 파이프라인 작동 원리 순서상 정확히 몇 번째 단계인지 특정한다. ② 그 단계를 수정하면 변동되는 영향 범위를 전부 나열한다. ③ 범위의 항목마다 이 수정으로 영향이 있는지 없는지, 왜 그렇게 수정해야 하는지, 틀리다면 왜 틀린지를 전체 나열한다. ④ 접근 방향마다 전체 컨벤션 조항을 O·X로 판정하고, 다수결 원칙에 따라 O가 많은 방향으로 접근한다. ⑤ 그 접근을 증명하는 실측을 한다. ⑥ 실측 결과로 판단을 확정한다. ⑦ 확정한 판단이 컨벤션의 모든 조항을 만족함을 증명한 뒤에 이행한다. 비어 있는 단계가 있으면 그 단계의 사실을 얻는 행동을 먼저 한다([C00](#C00) 추론의 근거). 한 건의 이슈만 보고 가설을 세워 구현하는 것은 이 절차의 위반이다 |
| 로직 단위 컨벤션 판정 | 코드·도구를 실행하거나 결과를 확정하기 전에, 그 실행이 거치는 파일을 의존성 순서로 놓고 첫 파일의 첫 로직부터 로직 하나마다 이 문서 전체 조항에 대해 근거(지시 원문, 원본 기록, 실측, 공식 출처)를 확보해 OK를 판정한다. 로직 하나가 OK여야 다음 로직으로 가고, X이거나 근거가 없는 로직은 그 자리에서 근거를 얻어(원문 읽기·등록 도구 조회·실측) 고친 뒤 다시 판정한다. 실행하는 모든 로직이 OK일 때만 그 코드·도구를 실행한다. 구문·정적 검사는 정적 범위의 진단일 뿐 로직 판정의 증거가 아니다. 근거가 없다는 이유로 실행·작업을 거부하거나 멈추지 않으며, 그 근거를 얻는 행동을 먼저 한다. 판정 전에 실행해 보고 결과로 확인하는 실행, 실패 뒤 같은 도구의 반복 실행, 위반의 인정·사과·나열로 교정과 실행을 대신하는 응답을 금지한다. 기존 코드의 존재는 판정 근거가 아니다([C01](#C01)) |
| 성능 병목 보고와 즉시 FIX | 병목마다 왜 병목인지, 논리오류일 수밖에 없음을 입증하는 서로 구별되는 수학적·소스 근거, 관련 파일 전체, 올바른 수정 방향과 그 증명, 전체 적용 조항의 O·X를 기록한다. 일반적인 관념은 근거가 아니다. 위 변경 판단 ①~⑦의 근거가 채워져 전체 적용 조항이 O로 일치한 병목은 발견 즉시 원인 소유자와 연결된 소비자를 FIX하고 같은 입력·조건의 전후 결과를 기록한다 |
| 명제 | 하나의 근거가 하나의 명제를 지지한다([C09](#C09)). 명제는 참·거짓을 관찰로 판정할 수 있는 문장이다 |
| 전수 요구 | "모든·전체·전수" 요구는 원본 목록을 전수 추출해 대조한다. 산출물 기준 열거, 한 단계 glob, 표본, 임의 필드 선택으로 대상 집합을 정하지 않는다 |
| 부재 주장 | 검색 범위와 방법을 명시한 경우에만 "없다"고 쓴다. 실패한 조회 한 번은 부재의 증거가 아니다 |
| 판정 구분 | 확인됨(관찰로 입증), 근거 있는 추론(연결은 있으나 관찰 없음), 미검증을 섞지 않는다 |
| 위반·미완료의 처리 | 컨벤션 위반은 수용되지 않은 미완료이며 표기만 남겨 방치하거나 종료하지 않는다. 실행 가능한 조사·증명·교정·연결·검증을 즉시 계속하여 해당 요구의 실제 수용 근거를 채운다. 문서 작성·참조 검사·계획 제시를 제품 위반의 해소 증거로 대신하지 않는다 |
| 미사용과 창작 | 원본이나 지시에 근거가 있는데 소비자가 없는 정의는 구현 누락이며 연결한다. 원본이나 지시에 근거가 없는 규칙·값·기능은 창작이며, 원본 값으로 대체하거나 제거한다 |
| 정방향 검증 | 지시의 모든 요구가 [C07](#C07)에서 그 작업 유형이 정한 결과와 수용 근거를 갖췄는지 확인한다. 하나라도 없으면 누락이다 |
| 역방향 검증 | 모든 변경·결과·보고 문장이 근거 요구나 조항으로 거슬러 올라가는지 확인한다. 하나라도 없으면 창작이다 |
| 수용 | 정방향과 역방향이 모두 통과하고, 정해진 검사가 오류 0·경고 0일 때만 수용한다 |

## 작업 수명주기·GOAL·트래킹

사용자가 한 세션에 입력한 지시 전체가 그 세션의 GOAL이다([C00](#C00)). 모든 AI는 아래 순서를 따른다. 단계별 도구 호출 절차는 AGENTS가 소유한다.

| 단계 | 반드시 할 일 | 끝 조건 |
| --- | --- | --- |
| 세션 시작 | 새 세션(`startup`·`clear`)에서는 다른 모든 행동보다 먼저 이 컨벤션 전문을 한 줄도 빠짐없이 정독하고, 이어서 [AGENTS]({{link.agents}}) 전문을 정독한다. 긴 문서는 모든 줄을 돌려주는 범위로 나누어 끝까지 읽으며, 요약·검색·부분 읽기로 정독을 대신하지 않는다. 그 뒤 {{generated.contextSourceDoc}}, 트래킹의 최신 요약·관련 미완료 TODO를 확인하고 적용되는 스킬 절차를 읽는다. 세션 압축(`compact`) 뒤에는 프로젝트 훅([C16](#C16))이 컨벤션 요약 표와 원문 위치·해시, 행동 요약 위치·해시, 트래킹 최신 요약·프로젝트 노드 표, 미완료 TODO를 무조건 문맥으로 제공한다. 압축 뒤와 같은 작업의 재개(`resume`·`fork`)에는 전체 재독 대신 최근 작업과 관련된 조항·절차·소유 파일이 여전히 맞는지만 범위를 정해 확인하고 이어서 작업한다. 유효한 근거는 유지하고 변경되거나 새로 필요한 조건·값·금지·수용만 확인하며, 요약의 생략은 조항 면제가 아니다 | 새 세션의 컨벤션·AGENTS 전문 정독, 압축 뒤 맥락 요약 제공, 현재 소유 원문과 적용 조항·남은 TODO 확인 |
| 지시 수신 | 입력을 원자 요구로 나누고, 원문·대상·수용 조건을 작업 기록에 한 행씩 남긴다. 작업 중에 들어온 입력도 즉시 같은 방식으로 병합한다 | 요구 누락 0 |
| 작업 중 | 모든 행동은 요구나 조항으로 거슬러 올라가야 한다. 진행 보고는 한국어 한 줄이며 실행을 대체하지 않는다. 실패는 [C06](#C06) 원인 수정으로 처리한다. 백그라운드 작업은 결과를 회수한 뒤 다음 단계로 간다. 작업이 진행되는 동안 트래킹의 진행 기록 절에 요구별 변경·근거·남은 일을 시각과 함께 계속 갱신한다. 멈춤·미룸·축소, 핸드오프 작성을 금지한다 | 요구별 구현 진행과 진행 기록 갱신 |
| 검증 | [C14](#C14) 양방향 검증과 [C12](#C12)의 변경 유형별 고정 검사를 한다 | 누락 0, 창작 0, 오류 0·경고 0 |
| 완주·기록 | GOAL의 모든 요구가 증거를 갖췄을 때만 트래킹에 세션 요약을 쓴다. 완주 전에는 세션 요약 대신 진행 기록만 갱신한다 | 요약 작성 |
| 기록 직후 대조 | 쓴 요약을 이 문서 조항별로 대조한다. 어긴 조항이 있으면 그 작업을 다시 하고 요약을 고친다 | 위반 0 |
| 응답 | 짧은 한국어로 결과 → 요구별 증거 → 미검증 경계 → 남은 TODO 순서로 보고한다. 최종 응답과 도구 호출 사이의 진행 응답 모두 해당 행동의 근거인 컨벤션 조항 번호를 반드시 표기한다. 조항 표기는 실제 적용 근거와 연결하며 준수·완료의 증거를 대신하지 않는다. 모든 최종 응답과 진행 응답은 보고하는 행동마다 `harness.config.json` `response.fields`의 항목({{generated.responseFieldList}})을 항목 이름 그대로 담고(첫 항목은 근거 컨벤션 조항 번호와 그 규칙), 각 항목은 그것을 확정하는 원본 경로·실측·관찰을 적는다. 모든 응답은 "…을 기반으로 …을 이행하고, 행함에 따른 근거는 다음과 같아요" 문장, 번호 붙은 근거 1, 근거 2, …(각각 원본 경로·실측·관찰), 그 근거로만 이끈 따라서 결론을 담는다. 추측이나 일반론은 근거가 아니다. 도구를 호출하는 어시스턴트 메시지에는 그 호출 전에 그 도구·접근 방식을 정의한 이 문서의 조항 번호와 행을 지목하고, 그 행에 대해 확인한 근거를 {{generated.basisLabelList}} 중 해당하는 이름으로 원본 경로·실측·관찰과 함께 적으며, [C16](#C16) 프로젝트 훅이 모든 도구 호출 직전에 이 조건을 문맥으로 주입한다([C00](#C00) 도구·접근 방식). 이 항목은 프로젝트 전체 응답 규칙이며, 프로젝트 훅이 세션 시작·지시 수신 문맥에 안내하고 종료 때 최종 응답에서 빠진 항목을 차단한다. 응답 어투는 정중한 존댓말로 고정하며 반말을 쓰지 않는다. 어투는 문장의 느낌만 바꾸고, 사실·근거·미검증 경계의 정확도는 줄이지 않는다. 증거 없는 완료 표식을 쓰지 않는다. 도구 호출 사이의 진행 문구와 영어 문서·도구 출력·요약을 읽은 직후의 첫 문장까지, 사용자에게 보이는 모든 문장은 한국어다. 추론 언어는 제한하지 않는다 | 적용 조항 표기 누락 0, 응답 필수 항목 누락 0, 도구 호출 근거 표기 누락 0, 허위 완료 0, 사용자에게 보인 영어 문장 0 |

트래킹 문서는 다른 기여자도 AI로 읽는 문서이므로, 모든 기록을 한 줄 요약 형식으로 압축해 쓴다. 한 기록은 한 줄이며, 그 줄은 요구의 요지와 결과를 판정하는 데 필요한 대상·근거·수치·미검증 경계·남은 일만 담는다. 트래킹에는 사용자 지시를 인용하지 않는다. 요구는 인용 부호로 옮긴 지시 원문이 아니라 요지로 쓰며, 지시 원문은 작업 기록([C12](#C12))에만 둔다.

진행 기록의 형식은 갱신마다 한 줄 `- 갱신 시각({{time.label}}) | 요구 요지 | 변경 | 근거 | 남은 일`이며, 최신 줄이 맨 위에 온다.

트래킹의 프로젝트 노드 절(`## 프로젝트 노드`)은 프로젝트를 이루는 노드([C04](#C04) 도메인·클래스 폴더, [C03](#C03) 계층, [C10](#C10) 컴파일 영역)를 한 행씩 관리한다. 행 형식은 `| 노드 | 경로 | 소유 조항 | 역할 | 의존 노드 | 상태 |`이며 상태는 `계획`·`구현 중`·`검증됨` 중 하나다. 노드를 추가·이동·삭제하거나 의존을 바꾸는 변경은 같은 작업에서 이 표를 고치고, 상태는 그 노드의 [C07](#C07) 수용 근거가 생겼을 때만 `검증됨`으로 바꾼다. 세션 압축 뒤 프로젝트 훅은 이 표를 문맥으로 제공한다([C16](#C16)).

트래킹의 세션 요약 형식은 다음과 같고, 최신 요약이 진행 기록 절 바로 아래 맨 위에 온다.

- 제목: `## YYYY-MM-DD 세션 GOAL 요약`
- GOAL의 요구마다 한 줄: `요구 요지 | 대상·방법 | 결과·검증 | 미검증 경계`
- 마지막 한 줄: `컨벤션 대조 | 대조한 조항 | 위반 0 또는 위반 조항과 재작업 결과`

이전 실패와 이후 수정의 인과를 합쳐서 지우지 않는다. 사용자가 트래킹 압축을 지시하면 이미 쓴 기록도 이 형식으로 압축하며, 날짜가 있는 모든 기록과 같은 날짜 안의 순서, 이전 실패와 이후 수정의 구분, 미검증 경계와 남은 일은 보존한다.

사용자가 AI의 반복 실패를 트래킹에 박제하라고 지시하면, 그 실패를 행동·시각·어긴 조항·결과로 트래킹의 박제 절에 기록하고, 다시 하지 않도록 막는 금지 규칙은 [AGENTS]({{link.agents}}) 6절에 같은 작업에서 추가한다. 박제 절은 세션 요약이 아니며 GOAL 완주를 기다리지 않는다.

일지·트래킹·기록에 쓰는 모든 시각은 {{time.label}} 기준이며, 손으로 계산하거나 시간대를 가정하지 않고 [C12](#C12) 시각 명령으로 확인한 값을 쓴다. 이 명령이 작업일지 시각의 단일 원천이다.

세션 감사의 TODO는 두 경우에만 갱신한다.

- 사용자가 TODO의 정리·고정·보완을 지시할 때
- 관찰된 외부 의존성, 상위 제약, 사용자의 세션 종료로 요구가 미완료인 채 세션을 넘길 때

트래킹의 세션 요약은 GOAL을 완주한 뒤에만 쓴다. 진행 중인 GOAL은 트래킹 맨 위의 진행 기록 절에 갱신 시각과 함께 쌓으며, 진행 기록은 세션 요약을 대신하지 않고, 이미 쓴 진행 줄은 위의 압축 지시 외에는 고쳐 쓰지 않는다. 두 문서의 역할은 겹치지 않는다.

## 전체 함수·파일 명명 규칙

자체 작성 함수 전체에 적용한다. 공개·비공개 함수, 메서드, 콜백, 훅, UI 컴포넌트, 셰이더 함수, 도구 함수가 포함된다. 외부 API 고정 이름·원본·생성물은 원 계약을 보존하고 자체 어댑터·생성기에서 이 규칙을 적용한다. 고정 진입점 예외를 일반 함수까지 확대하지 않는다.

| 대상 | 함수·심볼 이름 | 파일·고정 경계 |
| --- | --- | --- |
| TS·JS 일반 함수·메서드 | lowerCamelCase, 동작+대상 | export 파일명=심볼명 |
| TS 타입·인터페이스·클래스, UI 컴포넌트 | PascalCase, 대상·책임 | 표시 책임; 일반 로직을 컴포넌트로 위장하지 않음 |
| 훅 | `use`+PascalCase 대상 | 상태·반응성·수명 연결 |
| 상수 | UPPER_SNAKE_CASE | 변경 가능한 상태를 상수로 명명하지 않음 |
| C++ 함수·메서드 | lowerCamelCase | 타입 PascalCase, 선언·구현 쌍; 생성자·소멸자·연산자·`main`은 언어 계약 |
| Rust 함수·변수 / 타입 | snake_case / PascalCase | 모듈 파일 snake_case |
| Go 함수·메서드·타입·상수 | MixedCaps. 공개 이름은 대문자, 비공개 이름은 소문자로 시작한다(Go 언어의 공개 규칙). 상수도 MixedCaps로 쓰며 이 행이 상수 행보다 우선한다(Effective Go) | 패키지 폴더는 소문자 한 단어(Effective Go)이며 `util`·`common`·`misc` 같은 의미 없는 패키지 이름을 쓰지 않는다(Go 블로그 "Package names"). 파일은 snake_case(프로젝트 선택) |
| Python 함수·메서드 | snake_case | 파일 snake_case; `main`·특수 메서드는 실행·언어 계약 |
| PHP 함수·메서드 / 클래스 | lowerCamelCase / PascalCase | 클래스 파일명=클래스명 |
| C# 메서드·속성·타입 | PascalCase | 지역 변수·매개변수 lowerCamelCase |
| 셰이더 함수 | lowerCamelCase | 진입점은 해당 API 계약 |

이름은 책임·입력·결과·부작용·수명과 일치해야 한다. 같은 도메인 개념은 같은 용어, 다른 개념은 구별되는 이름을 사용한다. 대소문자만 다른 파일·export, 동명 별칭 충돌, 의미 없는 번호·`new`·`temp`·`misc`·`manager`만으로 책임을 대신하는 이름을 금지한다. 기존 이름에 단어가 포함됐다는 이유만으로 무관한 개명을 시작하지 않는다.

| 이름의 의미 | 판정 규칙 |
| --- | --- |
| `get`·`read`·`find` | 조회 대상·위치·실패 결과와 일치; 숨은 자원 생성·저장 금지 |
| `is`·`has`·`can` | 불리언 명제와 실제 반환 조건 일치; 가능 여부와 실행 성공 구분 |
| `create`·`destroy`, `attach`·`detach`, `register`·`unregister` | 실제 소유·해제·연결·등록의 수명 계약과 일치 |
| `load`·`save`·`write`·`export` | 입출력 경계·실패 전달·지속성 의미 일치; 메모리 변경을 저장 성공으로 명명하지 않음 |
| 계산·변환 | 대상·좌표계·단위 등 구별이 필요한 의미 식별; 원본 근거 없는 의미 부여 금지 |
| 비동기 | 이름·반환 타입·호출자의 대기 계약 일치; 접수를 완료처럼 표현하지 않음 |

선정 근거는 해당 소유자·호출자·입출력 계약이다. 개명의 수용 범위는 선언·파일·export·import·등록 키·선택자·직렬화/외부 소비자까지다. 정규식 통과는 철자 형식만 증명하며 의미 일치를 증명하지 않는다.

## 도구 사용 계약

도구는 아래 표의 용도와 방법으로만 쓴다. 표에 없는 도구, 표와 다른 방법, 표에 없는 위치는 금지다.

병렬 처리와 병목 처리는 선택이 아니라 컨벤션 계약의 필수 이행이다. 의존성이 없는 명시 조회는 정해진 동시 실행 한도 안에서 병렬 처리하고, 선행 결과를 요구하는 동작은 순서를 지킨다. 입력·결과 순서·개별 실패·자원 수명·사람의 입력 우선권을 보존한다. 도구에서 병목을 발견하면 입력·조건·시간·출력과 원인을 보존하고 [C06](#C06) FIX 프로세스로 즉시 책임 소유자와 영향 연결을 수정한다. 전후 비교는 동일 입력·조건·결과의 측정으로만 수용하며 코드 변경을 성능 해소 근거로 삼지 않는다. 이 의무는 AI 하위 에이전트 생성 권한을 부여하지 않는다.

모든 도구의 병렬·자원 계약: CPU 사용은 실행 중인 PC에서 운영체제가 보고한 물리 코어 수의 50%를 넘지 않는다. 워커 수는 물리 코어 수 × 0.5(내림, 최소 1)이고, 워커 하나는 연산 스레드 하나로 실행한다. RAM 사용은 전체 물리 메모리의 80%를 넘지 않는다. 작업을 내보내기 전에 사용 중 물리 메모리가 전체의 80% 이상이면, 실행 중인 작업이 끝나 그 아래로 내려갈 때까지 내보내지 않는다. 워커 수·스레드 수·작업 분할 수를 숫자로 하드코딩하지 않으며, 정적 분할도 하지 않는다. 무거운 작업은 독립 단위로 나눠 공용 대기열에 넣고, 쉬는 워커가 남은 단위를 가져간다. 단위 사이의 의존은 대기열 순서로 보장한다. 이 한도는 자원 경계이며 대상 일부를 전체 수용으로 계산하지 않는다.

도구는 통합이 기본이다. 생산·동기화·검사·실행 기능은 이 표가 지정한 소유 도구 안에 둔다. 소유 도구가 실패하거나 기능이 없으면 그 도구 안에서 원인을 고치고, 그 도구의 정식 진입점으로 실행한다. 조회·실측·대조·검증은 {{mcp.queryRoute}}로 한다. 임시 스크립트는 등록 도구에 그 기능이 없을 때만 `{{paths.scratch}}/`에서 사실을 조회하는 데 쓰며, 생산·동기화·데이터 기록 경로를 대신하지 않는다. 다음은 모두 우회이며 금지다.

- 소유 도구의 내부 함수를 떼어 인자·단계·입력을 바꿔 호출하는 실행기
- 실패 단계를 건너뛰거나 필수 인자를 빼는 래퍼
- 소유 도구와 같은 역할을 하는 별도 스크립트
- 등록 도구가 제공하는 조회·실측·대조를 대신하는 임시 스크립트

도구 폴더의 모든 파일은 서로 연결된 하나의 생산·검사 체계에 속한다. 각 파일은 정식 명령, MCP 서버 등록, [C17](#C17) 생산 도구, 그 도구가 단계로 호출하는 도구, 이들이 가져오는 모듈 중 하나다. 어디에도 연결되지 않은 독립 파일과 조회·검사·분석·일회성 보정 같은 임시용 파일을 두지 않는다.

| 미사용·미정의·단절 코드 | 삭제, 레거시로 분류 | 생산자 → 소비자 연결을 구현한다([C06](#C06)). 임시용 파일은 [C12](#C12) 도구 연결 규칙에 따라 두지 않는다 |
| 생산 도구 | 실패를 피하려는 우회 실행기·래퍼·복제 스크립트, 실패 단계 건너뛰기 | 그 도구 안에서 원인을 고치고 정식 진입점으로 실행한다([C12](#C12)) |
| git 이력 | 재작성, 강제 push, 훅 우회 | 사용자 지시 |

<a id="C09"></a>
## 근거·행동·기록 수용 기준

모든 행동에는 **누가·무엇을·언제·어디서·왜·어떻게**가 식별되는 직접 명제가 필요하다. 행동 권한은 지시·계약, 사실 판단은 해당 소스·설정·관찰 결과에 연결한다. 근거 하나와 그 근거가 실제로 지지하는 명제 하나를 1:1로 대응한다. 여러 전제가 필요하면 각 연결을 따로 입증한다. 차집합·부분집합·포함률·다수결·확신은 직접 근거를 대체하지 않는다. 다수결은 [C14](#C14) 변경 판단 절차 ④의 접근 방향 선택에만 쓰며, 그 뒤의 실측과 모든 조항 만족 증명을 대체하지 않는다.

참 판정에는 적용 조건·원인 연결·확인 결과, 거짓 판정에는 실제 반례 또는 위반 요구가 필요하다. 근거 없는 ‘없다’, 역사 문서를 현재 구현 증거로 쓰기, 모델 선택을 업계 표준으로 주장하기를 금지한다. 명제는 관찰로 참·거짓을 판정할 수 있는 진술이다.

행동 시작 게이트는 권한·대상·입력·방법·기존 근거, 끝 게이트는 결과·소비 연결·고정 검증이다. AI의 판단·도구 사용·수정·복구·완료에 적용하며, 응답 문장에 표식을 붙이라는 뜻이 아니다. 행동 순서는 AGENTS가, 세부 절차는 공유 워크플로우 스킬이 소유한다.

교정·오류·예외는 기존 요구나 상위 규칙을 소거하지 않는다. 실행 가능한 승인 작업이 남으면 같은 목표의 작업을 계속한다. 자체 금지·중단 조건, 임의 목표 축소, 사과·계획·상태 보고만으로 실행 대체를 금지한다. 실제 권한·외부 의존성·상위 제약은 그대로 적용하며 허위 완료나 금지 우회로 해결하지 않는다. 요구가 남아 있는 채로 미완료 증명 같은 표식을 붙여 응답을 끝내는 것을 금지하고, 남은 요구를 같은 목표에서 이어서 실행한다. 계획·문서에 빈칸 목록만 적거나 사용자 지시를 인용하는 문서 작업으로 구현을 대신하는 것도 금지하며, 근거로 확정한 논리는 같은 작업에서 바로 소스로 구현한다.

트래킹의 시점·형식과 응답 방법은 [C15](#C15)가 소유한다. 이 문서·AGENTS·스킬에는 세션 일지를 쓰지 않는다.

## 버전·자료 보존

버전 개념은 제품 버전 하나만 존재한다. 스키마·카탈로그·형식·프로토콜·파일 기록 등 그 밖의 모든 버전 필드·버전 번호·버전 비교는 금지하며, 레이아웃은 필드와 크기로 식별한다. 버전 값을 바꾸는 것으로 필드 제거를 대신하지 않는다. 제품 버전의 원천은 `{{version.source}}`이며, 다른 계층이 쓰는 버전 상수는 모두 이 한 값과 같다. 변경 도구는 `{{version.command}}`이며 커밋이 버전을 임의 변경하지 않는다. 구 경로와 새 경로, 또는 한 아키텍처 결정의 대체 구현 사이를 고르는 스위치(명령행 플래그·옵션 필드·설정·환경 변수·모드 인자)를 두지 않는다. 확정된 아키텍처는 경로가 하나다. 자산 커밋·강제 push·히스토리 재작성·가드 우회를 금지한다. 유효 원본·생산 자산·사용자 변경·실패 근거는 명시 정리 범위 밖에서 보존한다. 각 자료의 라이선스가 그 권한을 소유한다.

## 강제 수단

규칙은 아래 기계적 강제 수단으로 강제한다. 각 수단은 해당 이벤트에서 도구 호출·응답 종료·커밋을 차단하거나, 그 시점에 지켜야 할 조건을 모델 문맥으로 주입한다. 강제는 그 수단의 소스와 관찰된 판정으로 보고하며, 문서·설정을 고친 사실만으로 강제를 보고하지 않는다. 아래 수단이 판정하지 않는 규칙은 AGENTS·스킬 절차로 이행하고, 같은 위반이 반복되면 사용자 지시로 그 규칙을 아래 수단에 옮긴다.

| 수단 | 실제로 하는 일 | 강제 방식 |
| --- | --- | --- |
| 스택 검증 명령([C12](#C12) 스택 표) | 활성 스택의 정적·빌드 진단 | 종료값·수용 조건이 맞지 않으면 수용하지 않는다. 사후 훅이 편집 뒤 남은 검사를 기록하고, 종료 훅이 남은 검사를 알려 다음 행동을 이어가게 한다 |
| `.githooks/pre-commit` → [커밋 가드]({{link.commitGuard}}) | `harness.config.json` `commitGuard.blockedExtensions`의 확장자 파일 커밋 | 커밋을 종료 1로 차단한다. `git config core.hooksPath .githooks`로 연결하면 모든 에이전트와 사람의 커밋에 같이 적용된다 |
| 프로젝트 훅: {{generated.hookRegistrationDoc}} → [run_project_hook.mjs]({{link.hook}}) | 시작 훅은 입력의 `source`로 나눈다: 새 세션에는 컨벤션·AGENTS 전문 정독을, 압축에는 컨벤션 요약 표·행동 요약·트래킹 최신 요약·프로젝트 노드 표·미완료 TODO를 원문 위치·sha256과 함께 문맥 한도(10,000자) 안에서 추가하고, 재개에는 최근 작업 관련 확인을 안내한다([C15](#C15)). 지시 수신 훅은 요구 보존·도구 근거·스킬 적재·응답 항목 조건을 주입한다. 사전 훅은 질문·계획 도구, Windows에서 Claude Code의 Bash 도구, 보호 경로 편집([C13](#C13)), 이미 있는 파일의 `Write`·`Add File`, 삭제 후 재생성, 자체 코드의 주석 증가([C04](#C04) `no-inline-comment`), 켜진 인라인 규칙의 증가([C04](#C04) 핵심 규칙 표), 금지 경로, CMD·배치 경로, 활성 스택의 금지 명령, 금지 명령 목록, 전경 대기, 하네스 스크래치 경로, 시스템 임시 폴더 쓰기, 보호 폴더 셸 쓰기, 마지막 사용자 지시에 멈춤 지시가 없을 때의 작업 중지, 필요한 스킬이 적재되지 않은 변경·실행을 차단하고, 통과한 호출마다 도구 근거 조건([C00](#C00) 도구·접근 방식, [C14](#C14), [C15](#C15))을 주입한다. 사후 훅은 스킬 적재(Claude Code의 Skill 도구 호출, 또는 스킬의 `SKILL.md`를 읽은 성공한 도구 호출)를 기록하고, 편집 확장자에 따라 남은 검사를 표시하며, 검사 명령의 종료값·수용 조건이 맞을 때만 그 앞 편집의 남은 검사를 지운다. 종료 훅은 필수 스킬 미적재, 금지 판단 문구, 사용자 수준 게이트 표식, 보고 지시 없는 수긍·보고 문구, 존재하지 않는 조항 번호, 응답 필수 항목·근거 항목 누락, 근거 없는 항목 값, 존재하지 않는 인용 경로·줄, 추측 표현, 기반 문장·번호 근거·결론 누락을 차단하고, 남은 검사가 있으면 알려 작업을 이어가게 한다. 판정 문구·라벨은 `harness.config.json` `response`가 출력 언어별로 소유한다 | 사전·종료 훅은 종료 2로 도구 호출·응답 종료를 막고 차단 사유를 모델에 돌려준다(Claude Code·Codex 공식 훅 계약). 시작·지시 수신·사전·사후 훅은 `additionalContext`로 조건을 주입한다. 등록 파일을 바꾸면 에이전트를 다시 시작해야 새 등록이 적용되며, Codex는 프로젝트 신뢰와 `/hooks` 검토 뒤에 프로젝트 훅을 실행한다 |
| `.mcp.json`·`.codex/config.toml` | 등록된 MCP 서버의 연결 | 등록된 서버만 같은 명령으로 시작한다([C12](#C12) MCP 서버 등록 행) |

- 위 수단이 판정하지 않는 규칙의 위반은 [세션 감사]({{link.audit}})에 증거와 함께 기록한다.
- 같은 위반이 반복되면 사용자 지시로 그 규칙을 위 강제 수단에 옮긴다.
