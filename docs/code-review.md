# 코드 리뷰 방법론 — 컨벤션에 근거한 논리적·과학적 리뷰

[← 편집 도구 정의](edit-tools.md) · 다음: [언어별 핵심 지식](languages/README.md)

이 문서는 사람 리뷰어와 AI 리뷰어가 같은 방법으로 코드를 판정하게 하는 방법론이에요. 출발점은 하나예요: **코드는 프로젝트의 목적을 이루는 수단이고, 그 목적은 컨벤션에 선언돼 있다.** 그래서 리뷰의 판단 기준은 리뷰어의 취향이 아니라 컨벤션 조항이에요.

## 1. 리뷰의 정의

| 항목 | 정의 (컨벤션 C07 리뷰 행) |
| --- | --- |
| 범위 | 지정된 파일·패치·기능 → 그 변경이 도달할 수 있는 위반 |
| 산출물 | 위반마다 **위치 · 트리거 · 위반한 계약 · 영향** |
| 권한 | 리뷰는 보고를 허가해요. 리뷰만 지시받았다면 코드를 고치지 않아요 |

리뷰는 "이 코드가 마음에 드는가"가 아니라 **"이 변경이 선언된 목적·정의·계약을 지키며 그 목적을 향해 움직였는가"** 를 판정하는 일이에요.

## 2. 철학적 기초 — 왜 이 방법인가

### 2.1 목적에서 출발한다 (목적론)

같은 코드라도 목적이 다르면 옳고 그름이 달라져요. 캐시를 넣은 변경은 "응답 속도가 목적"인 프로젝트에서는 개선이고, "항상 최신 원본을 보여 주는 것이 목적"인 프로젝트에서는 결함이에요. 그래서 리뷰는 코드를 읽기 전에 **목적을 복원**해요: 요구(지시·이슈)와 그 요구가 걸린 컨벤션 조항(C02 확정 결정, C03 소유자, C04 구조…)을 먼저 확정해요. 목적이 선언되지 않은 영역의 판단은 리뷰어가 정하지 않고 "결정 필요"로 보고해요.

### 2.2 아는 것과 추정하는 것을 나눈다 (인식론)

리뷰 문장은 세 종류뿐이에요(C14 판정 구분).

| 종류 | 성립 조건 | 예 |
| --- | --- | --- |
| 확인됨 | 원문·실행·도구 출력으로 관찰 | "`quantity` 가 0일 때 합계가 0이 되는 것을 테스트 입력으로 확인" |
| 근거 있는 추론 | 연결은 있으나 관찰은 없음 | "`parseOrder` 가 `null` 을 반환할 수 있고(파일:줄), 호출부가 검사하지 않음(파일:줄)" |
| 미검증 | 연결도 관찰도 없음 | 보고서에 미검증으로 표시하고 결함으로 단정하지 않음 |

"보통 이렇게 한다", "더 깔끔하다"는 세 종류 어디에도 들지 않아요. 근거가 아니라 선호예요(C09).

### 2.3 결함은 반례로 증명한다 (반증)

"이 코드는 옳다"는 모든 입력에 대한 주장이라 관찰 몇 개로 증명되지 않아요. 반대로 "이 코드는 틀렸다"는 **반례 하나**로 증명돼요. 그래서 결함 지적은 반드시 **구체 입력과 시점(트리거) → 기대 결과 → 실제 결과**를 가져요. 반례를 만들 수 없으면 그 지적은 결함이 아니라 질문이나 미검증이에요.

### 2.4 증상이 아니라 원인과 소유자를 본다 (인과)

결함의 위치는 증상이 드러난 곳이 아니라 **계약을 어긴 소유자**예요(C06 FIX 정의: 트리거 → 기대와 실제의 불일치 → 위반 계약 → 책임 소유자 → 영향받는 생산자·소비자·생명주기). 증상이 드러난 곳에 방어 코드를 더하라는 제안은 원인을 숨기는 제안이에요.

## 3. 리뷰 절차

순서가 고정돼 있어요. 앞 단계의 증거가 다음 단계의 전제이기 때문이에요.

| 단계 | 하는 일 | 근거 조항 | 끝나는 조건 |
| --- | --- | --- | --- |
| ① 범위 고정 | 리뷰 대상 파일·패치·기능과 질문을 확정 | C07 | 대상 목록과 리뷰 질문 |
| ② 목적 복원 | 요구와 그 요구가 걸린 조항·확정 결정을 확인 | C00·C02 | "이 변경은 무엇을 위해 있는가" 한 문장 + 조항 번호 |
| ③ 파이프라인 위치 | 변경이 생산자 → 선택자 → 공유 인터페이스 → 소비자 → 생명주기 중 어디인지 | C03·C14 ① | 전체 흐름 속 단계 하나 |
| ④ 영향 범위 | 그 단계를 바꾸면 함께 움직이는 호출자·소비자·등록·설정·스키마 열거 | C14 ② | 원문에서 찾은 영향 목록 |
| ⑤ 계약 대조 | 소유자(C03), 구조·의존 방향(C04), 이름(C05), 오류·예외(C06), 도구 계약(C12), 보호 대상(C13) | 각 조항 | 조항별 O/X와 근거 위치 |
| ⑥ 실패 경로 | 외부 입력 실패, 부분 상태, 해제, 취소, 동시성 | C06 예외 처리 | 경로별 처리와 경계 계약 |
| ⑦ 반례 구성 | X로 판정한 항목마다 트리거 → 기대 → 실제 | C09·C14 | 재현 가능한 반례 또는 미검증 표시 |
| ⑧ 양방향 확인 | 정방향: 요구마다 구현·연결이 있는가 (누락 0). 역방향: 변경마다 요구·조항이 있는가 (발명 0) | C14 | 누락·발명 목록 |
| ⑨ 보고 | 결함마다 아래 4장 형식 | C07 | 보고서 |

## 4. 지적 작성 형식

```text
[위치]   src/order/logic/calculateOrderTotal.ts:14
[트리거] items = [{ price: 1000, quantity: 3 }] 로 calculateOrderTotal 호출
[기대]   3000 (C02 "주문 합계 = 단가 × 수량" 확정 결정)
[실제]   1000 — reduce 가 quantity 를 곱하지 않음
[계약]   C03 주문 합계 소유자 = order/logic. 소비자 checkout/ui 는 이 값을 그대로 표시
[영향]   결제 화면 합계, 영수증 생성(receipt/logic/buildReceipt.ts:22)
[근거]   원문 14행, checkout/ui/OrderSummary.tsx:31 의 소비
```

**좋은 지적** — 위 형식처럼 반례와 조항이 있어 작성자가 바로 재현하고 고칠 수 있어요.

**나쁜 지적** — "합계 계산이 좀 이상해 보여요. 보통은 유틸 함수로 빼는 게 좋아요."
이유: 트리거·기대·실제가 없어 재현할 수 없고, "보통은"은 근거가 아니며, `util` 로 빼라는 제안은 C05 도메인 명명 규칙과 충돌해요.

## 5. 결함 분류

| 분류 | 판정 질문 | 대표 조항 |
| --- | --- | --- |
| 목적 위반 | 확정 결정·요구와 다른 결과를 내는가 | C02 |
| 연결 누락 | 만든 것이 실제로 선택·등록·소비되는가. 정의만 있고 소비자가 없는가 | C03·C06 |
| 숨김 | 빈 catch, 근거 없는 기본값·폴백·재시도, 진단 억제, 검사 완화가 있는가 | C06 |
| 구조 | 소유자 밖에 공유 개념(타입·상수·로직·스타일)을 만들었는가, 의존 방향을 어겼는가 | C04 |
| 명명 | 이름이 실제 책임·입출력·부작용·생명주기와 일치하는가 | C05 |
| 생명주기 | 생성·해제, 등록·해제, 비동기 순서가 짝을 이루는가 | C03·C06 |
| 도구·보호 | 생성물·외부 코드·잠금 파일을 정해진 경로 밖에서 바꿨는가 | C12·C13 |
| 성능 | 같은 입력·조건에서 측정한 전후 값이 있는가. 측정 없는 성능 주장은 결함도 개선도 아님 | C14 |

## 6. AI가 쓴 코드에서 자주 나오는 결함

AI 모델은 "일단 동작하게" 만드는 쪽으로 공백을 채우는 경향이 있어요. 리뷰는 아래를 먼저 봐요.

| 패턴 | 왜 결함인가 | 하네스 연결 |
| --- | --- | --- |
| 조용한 폴백 (`?? defaultValue`, `catch { return [] }`) | 실패를 정상 값으로 바꿔 원인을 숨겨요 | C06 숨김 금지 |
| 매직 리터럴 (`if (status === 3)`, URL·경로 직접 기입) | 값의 의미와 소유자가 사라져요 | `no-magic-literal` 규칙 |
| 인라인 타입·스타일·핸들러 | 공유 개념이 소유자 밖에 흩어져요 | `no-inline-type`·`no-inline-style`·`no-inline-handler` 훅 |
| 의도를 주석으로 설명 | 이름과 구조가 의도를 담지 못한다는 신호 | `no-inline-comment` 훅 |
| 정의만 있고 호출되지 않는 함수 | 연결 누락 | C06 미사용 = 연결 누락 |
| `util`·`helper`·`manager` 이름 | 책임을 숨겨요 | `domain-naming` 규칙 |
| 요구에 없는 기능 추가 | 발명 | C14 역방향 검증 |
| 테스트를 구현에 맞춰 수정 | 계약이 아니라 현재 동작을 고정해요 | C14 |

## 7. 리뷰어가 하지 않는 것

- 취향을 결함으로 보고하지 않아요. 선호는 "제안"으로 분리하고 근거가 없음을 밝혀요.
- 작성자의 설명을 증거로 쓰지 않아요. 설명은 가설이고, 원문과 실행으로 확인해요.
- 테스트 통과를 정확성의 증거로 쓰지 않아요. 테스트는 그 테스트가 검사한 계약만 증명해요.
- 리뷰 범위 밖 파일을 함께 고치라고 요구하지 않아요. 발견한 범위 밖 문제는 한 줄로 따로 적어요.
- 리뷰만 지시받았을 때 코드를 고치지 않아요.

## 8. AI 에이전트에게 리뷰를 맡길 때

1. 범위와 질문을 정해서 지시해요: "`src/order/` 변경을 C03·C04·C06 기준으로 리뷰하고, 결함마다 위치·트리거·계약·영향을 보고해".
2. 서브 에이전트에게 두 번째 의견을 받을 수 있어요(`node .harness/subagents/run_subagent.mjs <id> <작업 파일>`). 서브 에이전트의 지적도 미검증 관찰이므로, 메인 에이전트나 사람이 원문으로 확인한 것만 채택해요.
3. 리뷰 결과로 고칠 때는 별도의 수정 지시로 FIX 절차(C06)를 시작해요.
